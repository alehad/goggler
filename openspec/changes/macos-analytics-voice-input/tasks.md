- [x] **Found and fixed two real crashes during manual testing, same root cause, two separate closures**: `EXC_BREAKPOINT`/`dispatch_assert_queue_fail`/`_swift_task_checkIsolatedSwift`, confirmed via real crash reports each time — the Swift 6 `@MainActor`-inference issue already hit twice elsewhere in this codebase, which the design's first draft only partially guarded against.
  - First crash: `SFSpeechRecognizer.requestAuthorization`'s completion handler fired off the main thread. Fixed by marking `requestAuthorization()` `nonisolated` (it touches no instance state, so needs no isolation at all) — `CheckedContinuation.resume` is safe from any thread.
  - Second crash (a fresh rebuild with the first fix applied still crashed — confirmed via a second, later crash report pointing at a *different* closure): the audio tap's completion closure, `{ buffer, _ in request.append(buffer) }`, installed on `AVAudioEngine`'s real-time render thread. Despite capturing only a local `request` variable — no `self`, no MainActor state — it was still inferred `@MainActor`-isolated purely from being lexically nested inside `start(...)`, a method on a `@MainActor` class (the exact same lexical-inference behavior already documented for `computeAnalyticsItems`, which had no `self` reference either and crashed for the identical reason). This is the concrete proof that "avoid touching `self`/MainActor state" is not sufficient by itself — the closure itself needs explicit `@Sendable` regardless of what it captures. Fixed by marking it `@Sendable`.
  - The recognition-task closure was also marked `@Sendable` (not just wrapped in `Task { @MainActor in }`, which alone doesn't stop the *outer* closure itself from being invoked off-thread) — this in turn required storing `onTranscript`/`onFinish` as instance properties rather than capturing them directly (mirroring `EbayAuthService.session`), since a `@Sendable` closure can only capture `Sendable` values and these caller-supplied callbacks close over `AnalyticsView`'s `@State`.
  - `@preconcurrency import Speech` added to silence the one remaining warning (`SFSpeechAudioBufferRecognitionRequest` isn't marked `Sendable` by Apple, despite being documented as safe to use exactly this way from the real-time audio thread) — a real gap in Apple's own framework annotations, not a real safety issue.
  - Swift 6 strict concurrency checking caught everything else at compile time once the `@Sendable` annotations were in place, rather than requiring more runtime crash-and-fix cycles. Final build: zero warnings from this file, 35/35 tests still pass.

- [x] Run dual security review (security-review skill + Copilot CLI). **Found and fixed two more real issues** (resource-lifecycle/privacy, not classic exploits):
  - Switching to another sidebar tab while voice input is actively listening deallocated `AnalyticsView`'s `voiceService` with no explicit `stop()` — the mic button (and its "stop" affordance) disappears from screen while `AVAudioEngine` could still be capturing audio, relying on ARC teardown timing rather than an explicit release. Fixed with `.onDisappear { voiceService.stop(); voiceListening = false }` on `AnalyticsView`'s root `ScrollView`.
  - If `audioEngine.start()` ever threw (no input device, mic claimed elsewhere, etc.), the catch block's `stop()` call was a no-op — `isListening` was still `false` at that point (only set `true` after `start()` succeeded), so `stop()`'s own guard skipped real cleanup, leaving the just-installed audio tap in place. A second attempt would then call `installTap` on a bus that already had one, raising an uncatchable `!hasTapOnBus` exception and crashing — one recoverable failure would have permanently broken voice input for the rest of the app session. Fixed by moving `isListening = true` to immediately after the tap is installed, before `audioEngine.start()` is even attempted, so `stop()`'s cleanup actually runs on this failure path.
  - Confirmed clean: no transcript content is ever logged (only metadata — auth status, error domain/code/description); authorization is correctly awaited and checked before any audio capture begins; the on-device/cloud recognition fallback matches standard `SFSpeechRecognizer` usage and is disclosed in the Info.plist usage strings.
  - Rebuilt clean, 35/35 tests still pass, re-verified the app relaunches and runs correctly. Re-ran both reviews on the updated diff: fixes confirmed correct and complete by a targeted re-verification pass (walked `stop()`'s exact behavior in the post-fix failure state line by line; confirmed `.onDisappear` genuinely fires on tab switch since `ContentView`'s tab selection is a real structural `switch`, not a hidden/opacity trick).
  - **Third finding, independently confirmed by both reviewers (Copilot CLI: MEDIUM/9-confidence) — fixed rather than just documented**: the narrow window where switching tabs while `start()`'s `Task` is still suspended mid-`await requestAuthorization()` would let capture begin after the view (and its stop button) is already gone. Fixed: `AnalyticsView` now holds the start `Task` in `voiceTask` state, cancels it in `.onDisappear` alongside the existing `voiceService.stop()`; `VoiceInputService.start()` checks `Task.isCancelled` immediately after the authorization await returns and bails out — discarding the stored callbacks without calling them, since the view that supplied them is already gone — before ever touching the microphone or installing the audio tap.
  - **Fourth finding, from a final holistic re-verification pass**: the *manual* stop path (tapping the mic button a second time) had the identical gap — it called `voiceService.stop()` (a no-op while still suspended in authorization, since `isListening` is `false` at that point) and reset the UI to "not listening," but never cancelled `voiceTask`, so a slow permission dialog could still let capture start later with no stop affordance visible on screen — reachable by a plain double-tap of the mic button, not just a tab switch. Fixed by adding the same `voiceTask?.cancel()` to that branch. This finding only surfaced because the re-verification pass was asked to do a fresh holistic check rather than just re-confirm the specific prior fix — worth noting as a reason to keep doing that rather than narrowly re-checking only what changed.
  - Also confirmed on this same pass, no further action needed: no other suspension point exists in `start()` between the cancellation check and `audioEngine.start()` (a straight synchronous run, so nothing can interleave); `finish()` can't double-invoke `onFinish` (captures it locally, nils the property, so a second call sees `nil` and no-ops); no retain cycles or data races in the file as a whole. One low-priority, pre-existing cosmetic note left as-is (explicitly assessed as not blocking by the reviewer): `stop()` doesn't clear `onTranscript`/`onFinish`, so an in-flight recognition callback that fires just after a stop could still write a late transcript into `aiQuestion` — harmless on a single-user app, not introduced by this change.
  - Rebuilt clean after each fix, 35/35 tests still pass throughout.
  - **One more Copilot pass flagged app backgrounding (Cmd+Tab away) as unhandled — HIGH/9-confidence, "blocking".** Considered but deliberately not fixed, with the user's explicit sign-off: tab-switch and manual toggle-off (the two real gaps found above) are handled; app-level backgrounding is a narrower edge case for a personal, single-user app doing short voice queries (not long dictation), and `SFSpeechAudioBufferRecognitionRequest` already auto-terminates on a natural pause in speech regardless — the same behavior the web version relies on — so a backgrounded session would very likely end on its own within seconds even with no explicit handling. macOS's own system-level mic-in-use menu-bar indicator is also always present independent of this app's UI. Fixing this properly would need `NSApplication` deactivation-notification plumbing not used anywhere else in this codebase — judged disproportionate scope for this PR. Left as a known, explicitly-accepted gap; worth revisiting only if it turns out to matter in practice.
